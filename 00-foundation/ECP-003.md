## Resumo

Define a **raiz de todo o projeto**: o problema. O ECP começa em `Problem`, não em `Goal` — porque **Goal é uma resposta; Problem é a causa**. Um objetivo formaliza *para onde* ir; um problema formaliza *por que* existimos. Este documento define o **Problem Record**, o primeiro artefato de qualquer projeto, e a regra imutável de que toda entidade do protocolo é rastreável até um problema (Lei `L-1`).

---

## 1. Por que este documento existe

O usuário diz: *"Quero um ERP."*

Isso não é um problema. É uma **solução imaginada**. O verdadeiro problema pode ser:

```
Fechamento do caixa
  ↓
4 horas
  ↓
Meta
  ↓
15 minutos
  ↓
Então
  ↓
ERP
```

Perceba: o ERP talvez nem seja necessário. Talvez uma automação simples resolva. Sem um modelo formal de problema, a entidade trata a solução imaginada como verdade e otimiza a coisa errada.

O ECP corrige isso na origem: **nada começa por uma solução; tudo começa por um problema verificável.**

## 2. O que é um problema

**Problema** é a diferença verificável entre o estado atual e um estado desejado, com impacto observável e sem solução aceita a priori.

| Conceito | Natureza |
|---|---|
| **Problema** | A causa — a diferença indesejada verificável. |
| **Objetivo** | A resposta — o estado desejado que resolve o problema ([ECP-004](./ECP-004.md)). |
| **Solução imaginada** | Um rótulo de solução ("fazer um ERP") — não é problema nem objetivo. |

### 2.1 Anatomia de um problema

Todo problema declarável tem:

1. **Descrição** — a situação indesejada, observável e mensurável.
2. **Causa-raiz** — a condição que origina a situação (ou hipótese de causa, registrada como suposição).
3. **Impacto** — a consequência de não resolver (custo, tempo, risco).
4. **Dono** — a entidade responsável por decidir se vale a pena resolver.
5. **Evidência** — a observação que prova que o problema existe ([ECP-008](./ECP-008.md)).

## 3. O Problem Record

Todo problema é registrado como um **Problem Record** — o artefato raiz do projeto, anterior a qualquer Goal Record.

```
PROBLEM_RECORD
  id                    # P-001, P-002, ...
  description           # situação indesejada, observável
  root_cause            # causa-raiz ou hipótese (suposição)
  business_impact       # consequência de não resolver
  owner                 # entidade responsável
  evidence              # E-001 — evidência de que o problema existe
  severity              # crítica | alta | média | baixa
  constraints[]         # limites herdados (legislação, prazo)
  status                # identificado | aceito | resolvido | descartado
  resolved_by[]         # goals que o resolvem (G-…)
```

Exemplo mínimo:

```
problem:
  id: P-001
  description: Fechamento do caixa demora 4 horas.
  root_cause: Processo manual.
  business_impact: Alto.
  owner: Financeiro.
  evidence: E-001
```

## 4. O problema antes do objetivo

O Problem Record é o **antecessor obrigatório** do Goal Record ([ECP-004](./ECP-004.md)):

```
PROBLEM_RECORD                    GOAL_RECORD
  id: P-001              ───▶     problem: P-001
  description: Fechamento          target: 15 minutos
    do caixa demora 4h             success_metric: < 15 min
```

Isso cria **rastreabilidade completa**: de cada artefato e decisão até o problema que justifica a existência do projeto (Lei `L-1`, [ECP-000](./ECP-000.md)).

## 5. Soluções imaginadas não são problemas

A regra prática mais importante:

- "Quero um ERP" → **solução imaginada**. Perguntar: qual problema? Com que evidência?
- "Fechamento do caixa demora 4 horas" → **problema**. Observável, mensurável, com dono.
- "Reduzir para 15 minutos" → **objetivo**. A resposta ao problema.

Se um projeto começa com uma solução imaginada, o protocolo **recua**: transforma o rótulo em hipótese de solução e busca o problema que ela pretende resolver.

## 6. Regras normativas

### REGRA ECP-003.1 — Todo projeto inicia com Problem Record aprovado

**Problema que resolve** (Q1):
    Projetos que começam por solução imaginada otimizam a coisa errada;
    sem problema formalizado não há referência de existência.

**Quando aplicar** (Q2):
    No início de qualquer projeto ou ciclo de engenharia, antes de
    qualquer Goal Record, Discovery ou Research.

**Quando NÃO aplicar** (Q3):
    A sessões estritamente instrumentais já cobertas por um problema
    aprovado (ex.: correção trivial), desde que o Problem Record de
    referência esteja declarado.

**Verificação automática** (Q4):
    O primeiro Goal Record da sessão referencia um Problem Record
    `status: aceito` com `description`, `impact` e `evidence`.

**Evidências de conformidade** (Q5):
    Problem Record aprovado + Goal Record com `problem` referenciado.

### REGRA ECP-003.2 — Soluções imaginadas não substituem problemas

**Problema que resolve** (Q1):
    "Quero um ERP" é tratado como objetivo, e a entidade entrega a
    solução errada com perfeição.

**Quando aplicar** (Q2):
    Quando o requisito inicial é um rótulo de solução (sistema,
    framework, recurso) sem problema subjacente declarado.

**Quando NÃO aplicar** (Q3):
    Quando o problema já está formalizado e a solução é uma escolha
    deliberada registrada como decisão.

**Verificação automática** (Q4):
    Antes de contratos de solução, existe Problem Record; rótulos de
    solução são marcados como hipóteses até rastrearem um problema.

**Evidências de conformidade** (Q5):
    Problem Record + rastreio solução → problema.

### REGRA ECP-003.3 — Migração de problema raiz exige decisão

**Problema que resolve** (Q1):
    Quando o problema raiz muda no meio do projeto, manter o rastreio
    ao problema antigo (falso) violaria a verdade; re-rastrear tudo
    silenciosamente violaria a auditoria (Lei `L-1`).

**Quando aplicar** (Q2):
    Quando um Problem Record é invalidado, reescrito ou substituído
    por outro enquanto existem entidades dependentes.

**Quando NÃO aplicar** (Q3):
    Quando o problema não muda (o objetivo é ajustado dentro do mesmo
    problema) ou em projetos pré-exploração sem Problem Record.

**Verificação automática** (Q4):
    O Problem Record original recebe `status: deprecado` com referência
    ao sucessor (`superseded_by`); um **Decision Record** de migração
    reencadeia as entidades afetadas (Goals, Claims, Decisions) ao novo
    problema. Nenhuma entidade aponta para o problema deprecado.

**Evidências de conformidade** (Q5):
    Problem Record deprecado + Decision Record de migração + cadeia
    `Decision → Goal → Problem` atualizada sem elos órfãos.
