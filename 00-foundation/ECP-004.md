## Resumo

Define **em direção a quê** uma entidade decide e trabalha. Os modelos de decisão, conhecimento e evidência respondem *como* decidir — mas nenhum respondia *decidir em direção a quê*. Um objetivo é sempre a **resposta** a um **problema** ([ECP-003](./ECP-003.md)): primeiro identifica-se a causa, depois formaliza-se o estado desejado. Este documento define a estrutura do **Goal Record** e a cadeia `Problem → Goal → Claim → Knowledge → Assumption → Evidence → Decision`.

---

## 1. Por que este documento existe

O usuário diz: *"Faça um ERP."*

Isso não é um objetivo. É um **rótulo** — e, antes dele, existe um **problema** ([ECP-003](./ECP-003.md)): *fechamento do caixa demora 4 horas*. O objetivo é a resposta a esse problema:

```
Problema
  ↓
Reduzir tempo operacional
  ↓
Automatizar estoque
  ↓
Emitir NF
  ↓
Integrar financeiro
```

Sem um modelo formal de objetivos, a entidade pode:

- otimizar a coisa errada com perfeição;
- entregar o rótulo sem alcançar o resultado;
- decidir sem referência ao resultado desejado.

O ECP responde com o **Goal & Intent Model**: todo objetivo é a resposta a um problema formalizado, e antes de qualquer decisão existe um objetivo.

## 2. O que é um objetivo

**Objetivo** é um estado de mundo desejado, observável e verificável — não uma tarefa, não uma entrega, não um nome de sistema.

A estrutura de um objetivo segue a cadeia:

```
Goal
  ↓
Outcome          → o resultado observável de mundo
  ↓
Requirements     → condições que o resultado deve atender
  ↓
Constraints      → limites (tempo, custo, legislação, escopo)
  ↓
Success Criteria → critérios que provam que o resultado foi alcançado
  ↓
Metrics          → medições das success criteria
  ↓
Acceptance       → procedimento que aceita ou rejeita o resultado
```

Um rótulo ("faça um ERP") vira objetivo somente quando esta cadeia é preenchida de forma verificável.

## 3. O Goal Record

Todo objetivo é registrado como um **Goal Record** — o artefato que traduz um problema ([ECP-003](./ECP-003.md)) em estado desejado, e que precede qualquer outro registro de decisão.

```
GOAL_RECORD
  id                    # G-001, G-002, ...
  problem               # P-001 — problema que este goal resolve (Lei L-1)
  objective             # estado de mundo desejado
  outcome               # resultado observável
  requirements[]        # condições atendidas
  constraints[]         # limites declarados
  success_criteria[]    # critérios prováveis
  metrics[]             # medições dos critérios
  acceptance            # procedimento de aceitação
  business_value        # por que vale a pena
  stakeholders[]        # quem é afetado
  priority              # alta | média | baixa
  parent                # goal pai (decomposição) | —
  status                # proposto | aprovado | ativo | concluído | abandonado
  dependencies[]        # goals dos quais depende
```

Exemplo mínimo:

```
goal:
  id: G-001
  problem: P-001
  target: 15 minutos
  objective: Reduzir tempo de fechamento do caixa.
  business_value: Alto
  success_metric: Tempo médio < 15 minutos
  constraints: Legislação fiscal
  stakeholders: Operador, Gerente
  priority: Alta
```

## 4. Hierarquia e decomposição de objetivos

- Um objetivo pode ser decomposto em **subobjetivos** (`parent`), todos com o mesmo padrão de Goal Record.
- A decomposição só é válida se a soma dos subobjetivos **cobrir** as success criteria do objetivo pai.
- Todo nível da hierarquia é endereçável (`G-001`, `G-001.1`, …) e rastreável.
- Um subobjetivo nunca contradiz uma restrição herdada do pai.

## 5. O objetivo antes da decisão

O Goal Record é o **antecessor obrigatório** do Decision Record ([ECP-009](./ECP-009.md)). Toda decisão referencia um goal; todo goal referencia um problema (Lei `L-1`); todo goal é decidido contra evidência.

```
PROBLEM_RECORD    ──▶   GOAL_RECORD    ──▶   DECISION_RECORD
  id: P-001              goal: G-001          decision: D-003
  descrição:              problem: P-001      goal: G-001
    caixa 4h              target: 15 min      evidence: E-014
                                                confidence: 0.91
                                                risk: low
```

Isso cria **rastreabilidade completa**: de cada decisão até o objetivo e, finalmente, até o problema que justifica o projeto.

## 6. A cadeia de rastreabilidade

O ECP ordena os artefatos na sequência natural de qualquer projeto:

```
Problem     → por que existe?           (ECP-003)
  ↓
Goal        → em direção a quê?         (ECP-004)
  ↓
Claim       → o que se afirma?          (ECP-005)
  ↓
Knowledge   → o que sei / não sei?      (ECP-006)
  ↓
Assumption  → o que assumo?             (ECP-007)
  ↓
Evidence    → o que prova?              (ECP-008)
  ↓
Decision    → o que decido?             (ECP-009)
  ↓
Lifecycle   → como executo o ciclo?     (ECP-010)
```

Nenhum artefato é produzido sem o antecessor.

## 7. Regras normativas

### REGRA ECP-004.1 — Todo Goal Record referencia um Problem Record

**Problema que resolve** (Q1):
    Objetivos sem problema de origem são soluções imaginadas ("fazer
    um ERP") otimizadas sem referência de existência.

**Quando aplicar** (Q2):
    Na criação ou revisão de todo Goal Record.

**Quando NÃO aplicar** (Q3):
    A sessões instrumentais já cobertas por um goal aprovado, desde
    que o problem de referência esteja declarado no goal pai.

**Verificação automática** (Q4):
    Todo Goal Record possui campo `problem` preenchido com id válido
    e `status: aceito` no Problem Record correspondente.

**Evidências de conformidade** (Q5):
    Goal Records com `problem` referenciado + Problem Record existente.

### REGRA ECP-004.2 — Toda decisão referencia um objetivo

**Problema que resolve** (Q1):
    Decisões sem referência de objetivo não são auditáveis; não se
    pode responder "por que isto foi feito?".

**Quando aplicar** (Q2):
    Em toda decisão de transição (avançar, coletar, retroceder,
    escalar, parar).

**Quando NÃO aplicar** (Q3):
    A decisões puramente infraestruturais do próprio runtime (ex.:
    escolha de política de cache), que não alteram o caminho do
    objetivo.

**Verificação automática** (Q4):
    Todo Decision Record possui campo `goal` preenchido com id válido
    e existente na hierarquia.

**Evidências de conformidade** (Q5):
    Decision Records com `goal` referenciado + Goal Record existente.
