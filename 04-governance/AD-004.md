## Contexto

O `P-0003` revelou que o ECP não termina na `Decision` — existe uma segunda
cadeia operacional. E, com ela, um **ciclo fechado**, não uma sequência:

```
Decision → Execution Intent → Negotiation → Provider → Execution
        → Evidence (resultado) → Knowledge (atualizado) → (volta a Decision)
```

Isso implica que o ECP possui, na verdade, **dois domínios conectados**:

- **Grafo Cognitivo** — `Problem`, `Goal`, `Knowledge`, `Assumption`, `Evidence`, `Decision`.
- **Grafo Operacional** — `Execution Intent`, `Contract`, `Negotiation`, `Provider`, `Execution`, `Snapshot`.

Os dois se cruzam na **Decision** — possivelmente a entidade mais importante do
protocolo: o ponto onde o raciocínio se torna ação.

## Decisão — Princípio da Arquitetura Emergente

> **A estrutura física nunca lidera a estrutura conceitual.**

A ordem é sempre:

```
Conceitos → Relações → Comportamentos → Arquitetura → Código → Pastas
```

Nunca o contrário. A organização física do Runtime (pastas, módulos) **decorre**
do modelo descoberto — nunca o precede. A estrutura física é uma **consequência**
da arquitetura, não uma hipótese.

## Repercussão imediata

1. **Não reorganizar as pastas ainda.** A (re)organização física do `ecp/` será
   consequência do modelo descoberto (`P-0004`), não o ponto de partida.
2. **`P-0004` resolvido (incremento 4 / `D-0005`).** O modelo estrutural é de
   **múltiplos domínios relacionados** (cognitivo × operacional), cruzando na
   Decision. Veredito registrado em `EXP-001.md` §5.4 e materializado em
   `ecp/domains.py`.
3. **Nova entidade confirmada:** `Observation` (Execution → Observation →
   Evidence). Evidência é uma observação aceita, contextualizada e vinculada a
   uma decisão ou hipótese; nem toda observação vira evidência. Observation é
   rastreável a Problem pela decisão que a utiliza.
