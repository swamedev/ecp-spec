## Contexto

Até agora o Runtime era visto como um **consumidor** da SPEC:

```
SPEC
  ↓
Runtime
```

O Incremento 4 provou algo mais profundo: ao responder o `P-0004`, o Runtime não
*implementou* uma classe `Observation` — a entidade **emergiu de uma lacuna
conceitual**. O ciclo real foi:

```
Pergunta → Problema → Hipóteses → Evidências → Implementação → Nova entidade
```

Isso é **produção de conhecimento a partir da implementação**. O Runtime deixou
de ser consumidor passivo do protocolo e passou a participar da evolução dele:

```
SPEC
  ↓
Runtime
  ↓
Experimentos
  ↓
Evidências
  ↓
Nova SPEC
```

## Análise técnica — a lacuna que o `Observation` resolveu

Desde a Camada 1 existia um salto lógico escondido sob:

```
Execution → Evidence
```

A forma fiel é:

```
Execution → Observation → Qualification → Evidence
```

**Nem toda observação vira evidência.** Algumas observações são:
- descartadas;
- contradizem hipóteses;
- têm baixa confiabilidade;
- precisam de validação.

Formalizar `Observation` como entidade de primeira classe torna esse processo
**explícito e auditável**. Ela não é um ajuste de glossário — é um modelo próprio.

## Suposições a confirmar por evidência (não por intuição)

- `A-030` — existem **pelo menos três domínios**: Cognitive, Operational e
  Governance (0.80).
- `A-031` — o conceito de *um único grafo* tornou-se pequeno demais; o correto é
  um **Tecido de Conhecimento** (Knowledge Fabric) de domínios interligados (0.80).
- `A-032` — a separação por **domínios** (e não por entidades) muda a futura
  organização física do pacote `ecp/` (0.70).

## Decisão

1. **O Runtime é um instrumento científico.** Ele produz conhecimento sobre o
   protocolo e alimenta a revisão da própria SPEC — não apenas consome a especificação.
2. **O Runtime é o produtor.** Reconhecemos formalmente o valor já demonstrado no
   Incremento 4, e o tratamos como critério de sucesso contínuo do Validation Program.
3. **Refórmula a definição do `P-0005`.** A pergunta deixa de ser *"qual é o
   modelo de domínio canônico?"* (organização) e passa a *"qual é a **ontologia
   canônica** do ECP?"* (existência). "Domínio" é **organização**; "ontologia" é
   **existência**. Ainda não sabemos quais entidades realmente existem. Objetivos:
   - quais entidades realmente existem;
   - quais são fundamentais;
   - quais são derivadas;
   - quais podem ser eliminadas;
   - quais aparecem **inevitavelmente** em qualquer projeto (pergunta mais importante).
4. **Não reorganizar o pacote `ecp/` agora.** A estrutura física é **consequência**
   da ontologia descoberta no `P-0005`, não uma hipótese antecipada (reforço do AD-004).
5. **`Observation` merece uma RFC própria — `ECP-011 (Observation Model)`.**
   Mínimos: definição formal; ciclo de vida; relação com `Execution`; critérios de
   promoção a `Evidence`; relação com `Confidence` e `Learning`; invariantes.
6. **O modelo multi-domínio merece um documento próprio — `RFC-001 (Knowledge Fabric)`.**
   O nome *grafo múltiplo* é recusado em favor de **Knowledge Fabric** (visão extensível:
   amanhã podem existir quatro ou cinco domínios). Conteúdo: domínios; entidades;
   ligações; regras de propagação; limites entre domínios. Servirá de base para a
   futura reorganização de código.

## Domínios identificados (provisórios, a confirmar no P-0005)

- **Cognitive Domain** — Problem, Goal, Knowledge, Assumption, Evidence, Decision.

## Hipótese central do P-0005 — H-005

> **H-005:** o ECP possui uma ontologia independente de qualquer implementação, e
> essa ontologia pode ser **descoberta** por experimentação dirigida a evidências.

A consequência metodológica é radical: **não inventamos classes — descobrimos
entidades.** Até hoje, nenhuma entidade (Execution Intent, Observation) foi
inventada; todas foram **descobertas**. O Runtime está descobrindo a ontologia do
protocolo. Como *problema* de engenharia, isso muda o objetivo: não "criar classes",
mas "descobrir entidades".

## Método — falsificação ontológica

Em vez de decidir o que existe, **tentamos destruir**: para cada entidade, responder
*se eu remover esta entidade, o protocolo continua funcionando?*

- Remover `Goal` → **não** funciona.
- Remover `Knowledge` → **não** funciona.
- Remover `Observation` → **talvez**, mas perde rastreabilidade.
- Remover `Execution Intent` → **talvez**, mas o Runtime fica pior.

A tabela fundamental (a ser preenchida por evidência no P-0005):

| Entidade | Essencial? | Evidência | Pode ser derivada? |
|---|---|---|---|
| Problem | ? | ? | ? |
| Goal | ? | ? | ? |
| Knowledge | ? | ? | ? |
| Observation | ? | ? | ? |
| Evidence | ? | ? | ? |
| Decision | ? | ? | ? |
| Execution Intent | ? | ? | ? |
| Contract | ? | ? | ? |
| Provider | ? | ? | ? |
| Snapshot | ? | ? | ? |

Só sobrevivem as entidades **indispensáveis** — essência justificada por evidência.

## Candidata a nova entidade (pré-ontológica)

Entre **Knowledge** e **Decision** parece faltar uma camada — a *interpretação
organizada* do conhecimento que fundamenta a decisão:

```
Realidade → Observações → Conhecimento → Modelo Mental → Decisão → Ação → Nova Realidade
```

Provisoriamente **Mental Model / Context Model / World Model**. Conhecimento isolado
não produz decisões; o que produz é a interpretação organizada desse conhecimento.
Nome a definir e existência a confirmar por evidência no P-0005. **É hipótese, não
decisão.**

## Novo tipo de RFC — RFC-D (Discovery)

Criação de **RFC-D (Discovery RFC)**, que registra **descobertas, não decisões**:

- `RFC-D-001` Observation
- `RFC-D-002` Execution Intent
- `RFC-D-003` Knowledge Fabric

Quando amadurecerem, podem ser **promovidas a RFCs normativas** — evitando
cristalizar conceitos cedo demais.

## Lema

> **A especificação governa. A implementação demonstra.**

## Repercussão

- O `P-0005` é o **próximo incremento** e responderá a **ontologia canônica** com
  o mesmo rigor dos anteriores (Problem → Goal → Knowledge → Assumptions →
  Evidence → Decision).
- Serão abertos os artefatos: `ECP-011` (Observation Model), `RFC-001` (Knowledge
  Fabric) e os `RFC-D-001..003` (Observation, Execution Intent, Knowledge Fabric),
  sem alterar a especificação vigente até suas resoluções.
- O método do P-0005 é a **falsificação ontológica**: preencher a tabela de
  essencialidade removendo cada entidade e observando se o protocolo sobrevive.
- Continua **proibida a reorganização física** de `ecp/` até o veredito do `P-0005`.

## Critérios de exit do `P-0005`

O incremento declara, com evidência: a **ontologia canônica** — quais entidades
são fundamentais, quais derivadas, quais elimináveis, e quais aparecem
inevitavelmente em qualquer projeto — com falsificação ontológica na tabela de
essencialidade e rastreabilidade do veredito.
