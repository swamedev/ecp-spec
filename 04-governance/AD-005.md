## Contexto

Até agora o Runtime era visto como um **consumidor** da SPEC:

```
SPEC
  ↓
Runtime
```

O Incremento 4 provou algo mais profundo: ao responder o `P-0004`, o Runtime não
*implementou* uma classe `Observation` — a entidade **emergiu de uma lacuna
conceitual**. O ciclo real foi:

```
Pergunta → Problema → Hipóteses → Evidências → Implementação → Nova entidade
```

Isso é **produção de conhecimento a partir da implementação**. O Runtime deixou
de ser consumidor passivo do protocolo e passou a participar da evolução dele:

```
SPEC
  ↓
Runtime
  ↓
Experimentos
  ↓
Evidências
  ↓
Nova SPEC
```

## Análise técnica — a lacuna que o `Observation` resolveu

Desde a Camada 1 existia um salto lógico escondido sob:

```
Execution → Evidence
```

A forma fiel é:

```
Execution → Observation → Qualification → Evidence
```

**Nem toda observação vira evidência.** Algumas observações são:
- descartadas;
- contradizem hipóteses;
- têm baixa confiabilidade;
- precisam de validação.

Formalizar `Observation` como entidade de primeira classe torna esse processo
**explícito e auditável**. Ela não é um ajuste de glossário — é um modelo próprio.

## Suposições a confirmar por evidência (não por intuição)

- `A-030` — existem **pelo menos três domínios**: Cognitive, Operational e
  Governance (0.80).
- `A-031` — o conceito de *um único grafo* tornou-se pequeno demais; o correto é
  um **Tecido de Conhecimento** (Knowledge Fabric) de domínios interligados (0.80).
- `A-032` — a separação por **domínios** (e não por entidades) muda a futura
  organização física do pacote `ecp/` (0.70).

## Decisão

1. **O Runtime é um instrumento científico.** Ele produz conhecimento sobre o
   protocolo e alimenta a revisão da própria SPEC — não apenas consome a especificação.
2. **O Runtime é o produtor.** Reconhecemos formalmente o valor já demonstrado no
   Incremento 4, e o tratamos como critério de sucesso contínuo do Validation Program.
3. **Abrir o `P-0005` — qual é o modelo de domínio canônico do ECP?**
   Estritamente **conceitual**, não de implementação. Objetivos: determinar
   - quais domínios existem;
   - quais entidades pertencem a cada domínio;
   - quais relações são permitidas;
   - quais relações são proibidas;
   - quais eventos propagam entre domínios;
   - quais invariantes preservam a consistência global.
4. **Não reorganizar o pacote `ecp/` agora.** A estrutura física é **consequência**
   do modelo descoberto no `P-0005`, não uma hipótese antecipada (reforço do AD-004).
5. **`Observation` merece uma RFC própria — `ECP-011 (Observation Model)`.**
   Mínimos: definição formal; ciclo de vida; relação com `Execution`; critérios de
   promoção a `Evidence`; relação com `Confidence` e `Learning`; invariantes.
6. **O modelo multi-domínio merece um documento próprio — `RFC-001 (Knowledge Fabric)`.**
   O nome *grafo múltiplo* é recusado em favor de **Knowledge Fabric** (visão extensível:
   amanhã podem existir quatro ou cinco domínios). Conteúdo: domínios; entidades;
   ligações; regras de propagação; limites entre domínios. Servirá de base para a
   futura reorganização de código.

## Domínios identificados (provisórios, a confirmar no P-0005)

- **Cognitive Domain** — Problem, Goal, Knowledge, Assumption, Evidence, Decision.
- **Operational Domain** — Intent, Contract, Negotiation, Provider, Execution,
  Observation, Snapshot.
- **Governance Domain** — AD, RFC, Experiment, Certification, Change.

*Esta listagem é uma hipótese de trabalho para o P-0005, não uma decisão final.*

## Lema

> **A especificação governa. A implementação demonstra.**

## Repercussão

- O `P-0005` é o **próximo incremento** e responderá o modelo de domínio canônico
  com o mesmo rigor dos anteriores (Problem → Goal → Knowledge → Assumptions →
  Evidence → Decision).
- Serão abertos os artefatos: `ECP-011` (Observation Model) e `RFC-001`
  (Knowledge Fabric), sem alterar a especificação vigente até suas resoluções.
- Continua **proibida a reorganização física** de `ecp/` até o veredito do `P-0005`.

## Critérios de exit do `P-0005`

O próximo incremento declara, com evidência: o modelo de domínio canônico —
quantos domínios existem, quais entidades por domínio, relações permitidas ×
proibidas, eventos de propagação e invariantes globais — com rastreabilidade do
veredito.
