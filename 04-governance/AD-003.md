## Contexto

O `EXP-001` (Bootstrap Runtime) mudou de natureza conforme era executado. O que
começou como "um caso real para provar o Runtime" tornou-se, de fato, **um
experimento sobre o próprio ECP**: a cada decisão que o Runtime toma, medimos se o
protocolo **melhora a qualidade da decisão** — não se o mecanismo funciona.

## Confirmações observadas (evidência empírica do EXP-001)

1. **O protocolo ampliou o espaço do problema.**
   + Pergunta inicial: *UUID ou ID estável?*
   + Pergunta reformulada pelo ECP: *como um sistema de identidade deve funcionar?*
   + Resultado: **Dual Identity** — uma arquitetura melhor que qualquer uma das
     duas alternativas iniciais. Comportamento exatamente esperado.
2. **O protocolo evitou decisão prematura.**
   Em desenvolvimento tradicional far-se-ia `id = uuid4()` e seguiria. O ECP obrigou
   a perguntar *por quê? para quem? em qual contexto? quais propriedades?* — gerando
   arquitetura melhor. **Este é um dado relevante para o Validation Program.**

## Decisão

1. **Refoco do Validation Program:** cada decisão do Runtime é tratada como um
   *ponto de medição* de se o ECP melhora a decisão — não como mera etapa técnica.
2. **Arquitetura do Runtime segue o grafo cognitivo, não módulos técnicos.**
   ❌ Recusada a organização típica de software:
   ```
   graph/  contracts/  providers/  storage/  engine/
   ```
   ✅ Adotada a organização pela **ontologia do protocolo**:
   ```
   ecp/
     problem/  goal/  knowledge/  assumption/  evidence/
     decision/  contract/  capability/  execution/  snapshot/  audit/
   ```
   Razão: o Runtime **não implementa tecnologias; implementa conceitos**. A distinção
   muda toda a arquitetura.
3. **Crescimento dirigido por perguntas** — cada incremento nasce de uma lacuna de
   conhecimento, não de uma funcionalidade:
   - `P-0001` *como implementar o Runtime?* → Kernel
   - `P-0002` *como identificar entidades?* → Dual Identity
   - `P-0003` *como transformar decisão em execução?* → (a definir por evidência)
4. **O `P-0003` é uma investigação, não "arquitetura de providers".**
   Objeto: *o mecanismo universal que transforma uma decisão autorizada em execução
   concreta, independente de tecnologia, preservando rastreabilidade, auditabilidade
   e capacidade de negociação.* Ao fim, se existir uma entidade nova (provisoriamente
   chamada **Execution Intent**) ou se o modelo atual bastar, **será decidido pelas
   evidências, não pela intuição.**

## Lema

> **A especificação governa. A implementação demonstra.**

## Repercussão

- O ciclo de retroalimentação saudável tornou-se operacional **antes** do previsto:
  `ECP-SPEC → ECP-RUNTIME → Experimentos (EXP) → Evidências → Revisão da SPEC`.
- O `P-0003` investigará o salto entre `Decision` e `Contract`, que ainda não está
  formalizado. Hipótese de trabalho: `Decision → Execution Intent → Contract → Execution`.
- Providers passam a ser **consequência da intenção de execução**, e não escolha
  antecipada: `Execution Intent → Negotiation → Provider → Execution`.
- O ARCHITECTURE encontra-se em `experiments/EXP-001.md` (cada incremento documenta
  Problem/Goal/Knowledge/Assumptions/Evidence/Decision e o veredito por evidência).

## Critérios de exit do `P-0003`

O próximo incremento declara, com evidência: (a) existe uma entidade nova que formaliza
o salto `Decision → Contract`, e o Runtime a materializa; ou (b) o modelo atual é
suficiente e tal entidade é desnecessária. Em ambos os casos, com rastreabilidade do
veredito.
