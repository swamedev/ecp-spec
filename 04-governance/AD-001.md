## Contexto

A especificação ECP atingiu um ponto em que o maior risco deixou de ser arquitetural e passou a ser o descolamento entre **teoria e prática**: a especificação cresceu mais rápido do que qualquer prova de que suas regras funcionam.

## Decisão

1. **O ECP-SPEC entra em Feature Freeze.**
   - ✅ Correções podem continuar.
   - ✅ Melhorias pontuais podem continuar.
   - ❌ Nenhum módulo grande novo (ECP-500 Quality, ECP-600 Learning, ECP-700 Certification) será iniciado enquanto a Fase B não produzir evidência.
2. **O programa muda de fase:**
   - Fase A (encerrada): criar a especificação.
   - Fase B (iniciada): provar a especificação.
3. **Será construído o ECP Reference Runtime (ERR)** — implementação canônica da especificação, à maneira de CPython para Python, SQLite para SQL e OpenSSL para TLS.
4. O Runtime será **100% agnóstico de implementador**: nunca chama GPT/Claude diretamente. A unidade de execução é a **Execution Unit** (LLM, Python, humano, Docker, API, script, workflow) — tudo igual sob a mesma interface. O conceito de `Capability` evolui para **Execution Provider**.
5. **O ECP Kernel vem primeiro**, com apenas cinco responsabilidades: `Problem`, `Goal`, `Decision`, `Contract`, `Graph`. Sem IA, sem API, sem CLI, sem banco — só lógica pura.
6. A missão da primeira versão: executar de forma íntegra, rastreável e reproduzível a cadeia:
   `Problem → Goal → Knowledge → Assumption → Evidence → Decision`

## Lema do programa

> **A especificação governa. A implementação demonstra.**

## Repercussão na especificação

- Roadmap alterado: os módulos `ECP-500..799` são reabertos **somente após** evidência da Fase B (ver `ROADMAP.md`).
- Nenhum documento de norma muda de status durante o freeze sem passar pelo processo de mudança (ECP-400).
- O repositório `ecp-runtime` vive em paralelo a `ecp-spec`: a implementação é a prova de que as regras funcionam.

## Critérios de saída da Fase B

1. O Kernel executa a cadeia `Problem → Goal → Knowledge → Assumption → Evidence → Decision` com integridade, rastreabilidade e reprodutibilidade.
2. Um primeiro caso real é conduzido integralmente pelo runtime.
3. O resultado é comparado com um processo tradicional usando critérios objetivos (tempo, rastreabilidade, facilidade de revisão).
4. Só então a evolução da especificação (Quality, Learning, Certification) é retomada, orientada pelas evidências.
