## Contexto

O **AD-001** iniciou a Fase B com o objetivo de *provar a especificação*. Ao
definir o primeiro caso real, surgiu uma exigência que o diferencia de um mero
"caso de teste": o caso **precisa demonstrar valor, não mecanismo**. O Kernel já
é provado pelos seus 14 testes; falta provar que o **ECP melhora a condução de um
projeto** — com tomada de decisão, pesquisa, hipóteses, mudança de entendimento e
rastreabilidade.

Qualquer projeto simples de reforço manteria um risco: o protocolo pode conduzir
bem casos triviais e falhar justamente nos que exigem trade-offs. O melhor objeto
para expor isso é um projeto com **solução não única** e **decisões arquiteturais
importantes** — e o candidato natural é o próprio Runtime.

## Decisão

1. **O primeiro caso real é "projetar o próprio ECP Runtime"** — o Runtime será
   desenvolvido usando o próprio ECP, do Problem Record à Implementação.
   - O Runtime é real, complexo, sem solução única, cheio de trade-offs e com
     decisões arquiteturais importantes — o que força o protocolo a trabalhar.
   - Se o ECP conduzir esse projeto do início ao fim, temos uma especificação
     que demonstra sua utilidade sobre a implementação que a valida.
2. **Hipótese formal do experimento (H-1):** *o ECP produz uma arquitetura mais
   justificável do que a abordagem tradicional.* Critérios objetivos: tempo,
   rastreabilidade, facilidade de revisão.
3. **Abrir uma fase permanente: Validation Program** — depois do Runtime, o
   percurso **não segue para Certification** imediatamente. Passamos a conduzir
   **experimentos numerados** sobre projetos reais.
4. **Experimentos planejados (numerados EXP-001..EXP-007):**

| EXP | Projeto | Pergunta |
|---|---|---|
| `EXP-001` | **Bootstrap Runtime** | O ECP conduz sua própria referência do início ao fim? |
| `EXP-002` | ERP | O ECP escala para um sistema grande com muitas entidades? |
| `EXP-003` | API | O ECP orienta decisões de interface/contrato? |
| `EXP-004` | Game | O ECP lida com produto de intenção aberta/iterativa? |
| `EXP-005` | Agente | O ECP guia um artefato com múltiplas capacidades? |
| `EXP-006` | Aplicativo | O ECP abrange app mobile/web de ponta a ponta? |
| `EXP-007` | Projeto externo | O ECP funciona fora do controle dos autores? |

   Cada experimento responde objetivamente: **o ECP ajudou? ou não?** — e alimenta
   a evolução da especificação (Quality/Learning/Certification) com evidência.

## Lema do programa

> **A especificação governa. A implementação demonstra.**

## Repercussão

- Criado `experiments/EXP-001.md` (Bootstrap Runtime) como primeiro experimento.
- ROADMAP reescrito: a fase **Fase B — Runtime** passa a ser absorvida pelo
  **Validation Program** permanente, com os experimentos como principal
  mecanismo de evidência (ver `ROADMAP.md`).
- O `ecp-runtime` continua em paralelo a `ecp-spec`; o **Decision Graph** gerado
  por `EXP-001` é o artefato de resultado (a memória de *por que* o Runtime é
  assim).
- Os módulos `ECP-500..799` permanecem congelados até que o Validation Program
  produza evidência suficiente (respeitando AD-001).

## Critérios de saída do Validation Program

A evolução plena de `Quality`/`Learning`/`Certification` é destravada quando o
Validation Program acumular evidência transversal de **múltiplos experimentos**
(não de um único), incluindo ao menos um domínio não controlado (EXP-007).
